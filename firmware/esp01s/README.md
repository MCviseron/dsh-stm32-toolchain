# ESP-01S Wi-Fi bridge (0.2.0)

Firmware for an ESP-01S (ESP8266, 1 MB) that lets the PC flash and talk to an STM32
over Wi-Fi instead of USB - the transport behind `transport: wifi`.

The ESP exposes **two** TCP servers and drives the STM32 reset lines, so the system
bootloader can be entered without touching the board.

| Port | Direction | Purpose |
| --- | --- | --- |
| 3333 | text, line based | control: `BOOT 0|1`, `NRST 0|1`, `PULSE [ms]`, `BOOTLOADER`, `RUN`, `WIFI`, `RESETWIFI`, `STATUS`, `PING`, `REBOOT` |
| 3334 | raw bytes | transparent pipe to UART0 (115200 8N1) = the STM32 USART |

## Wi-Fi credentials: three sources, in this order

| # | Source | Survives |
| --- | --- | --- |
| 1 | **EEPROM** - saved by the provisioning page | reboot, power loss, a normal reflash (not a full chip erase) |
| 2 | **wifi_creds.h** - generated by the plugin 生成固件 button | until the next generated build |
| 3 | **Provisioning AP** - both above failed | nothing is stored yet |

When neither 1 nor 2 connects, the ESP starts an access point instead of giving up:

1. join `STM32-ESP01S` (password `stm32flash`);
2. open `http://192.168.4.1` (a captive portal usually opens it for you);
3. type the SSID and password of the network the robot should use;
4. save - the ESP stores them in EEPROM and reboots into station mode.

`RESETWIFI` on the control port clears the saved credentials if you need to start over.

The control port answers `+WIFI mode=sta src=flash ssid=... ip=...` - `src` tells you which of the
three sources won (`flash` = EEPROM, `build` = baked in, `ap` = provisioning).

## Wiring

### ESP-01S to the STM32 (the product side)

| ESP-01S | STM32 | Note |
| --- | --- | --- |
| TX (GPIO1) | USART RX (PA10) | cross over |
| RX (GPIO3) | USART TX (PA9) | cross over |
| GND | GND | common ground is mandatory |
| 3V3 | 3V3 | **>= 300 mA peak**, 100 uF close to the module |
| GPIO2 | BOOT0 | firmware pin `PIN_BOOT0` (2) |
| GPIO0 | NRST | firmware pin `PIN_NRST` (0), **10k pull-up required** |

`GPIO0` must be HIGH while the ESP boots, otherwise it enters flash mode and never runs
the sketch - do not rely on the STM32 NRST pin to hold it high.

### Flashing the ESP-01S itself (USB-TTL, 3.3 V only - never 5 V)

| USB-TTL | ESP-01S |
| --- | --- |
| TXD | RX |
| RXD | TX |
| GND | GND |
| 3V3 | 3V3 + CH_PD (EN) |
| GND (jumper) | GPIO0 - only while powering up, to enter flash mode |

## Build and flash

The sketch is `esp01s.ino` (Arduino requires the file name to match the folder). In the
plugin you normally do not run these by hand: the panel Wi-Fi 名称 / Wi-Fi 密码 fields
plus 生成固件 and 烧到 ESP do exactly this.

```powershell
# by hand: bake credentials, then flash (GPIO0 grounded at power-up)
arduino-cli compile --fqbn 'esp8266:esp8266:generic:eesz=1M,xtal=80' --output-dir build .
arduino-cli upload -p COM5 --fqbn 'esp8266:esp8266:generic:eesz=1M,xtal=80' --input-dir build --verify
```

The plugin writes `wifi_creds.h` into a **temporary copy** of the sketch, so credentials never
travel through a command line (a password with quotes, spaces or `&` is safe) and never land
in the repository. Generated binaries go to `firmware/esp01s/build/`, which is gitignored - they
contain the password in plain text.

Verified builds: 315 KB of flash with credentials, 252 KB without.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| ESP prints garbage at 74880 baud, no TCP | sketch never ran: GPIO0 was low at boot |
| `+READY mode=ap` / `+STATUS mode=ap` | neither EEPROM nor baked credentials worked - connect to `STM32-ESP01S` and open `192.168.4.1` |
| Connects, then drops on every flash attempt | 3V3 rail cannot supply the ESP current peaks - add a bulk capacitor / stronger regulator |
| Pipe data appears but the STM32 never answers | TX/RX not crossed, or BOOT0 never went high (check `STATUS` while asserting it) |
| Bare `+ERR unknown` | command typo; the parser is case-insensitive but needs the space in `BOOT 1` |
