# 已知问题 / 待办

### 2026-10-25 晚 · 稳定性排查（进行中）

**现状**：端到端成功过一次（11 176 B / 7 s / 烧完回 `+PONG`），之后稳定卡在 `erase`。

**已确认稳定**：上传（44 片 CRC）+ `#Z` 整镜像校验 → 100% 成功。
**不稳定的一步**：`0x44/0x43` 擦除命令被 NAK（约 1/10 成功）。

**已实现的加固（固件，已编译未验证）**
1. 同步只认 ACK（`0x79`），失败则重新 `BOOT0 高 + NRST 脉冲` 再试，最多 3 轮；
2. 擦除失败 → 发 `0x7F` 拉回同步态再重试，最多 5 轮（日志 `+F retry erase n`）；
3. 每条命令发送前 **清空接收缓冲**（`uartDrain`），避免把上一轮的 `0x1F` 当成这次的回复。

**下一步（新会话按此顺序）**
1. 烧入 `esp32-spool-2026-10-25T17-46-11.bin`（含上述三项）；
2. 主机侧先确认 `0x7F → 79`、`0x02 FD → 79 01 04 13 79`；
3. 再跑 `flashSpool`，观察 `+F retry erase` 是否能自救；
4. 若仍失败：改用参考实现的"逐字节读取 + 100 次 0x7F 重试"结构，并打印每次命令的原始回执字节。

**已知易踩的坑**
- 不要给 AN3155 帧加人工间隙（会让 `0x31` 直接不 ACK）；
- `#S` 偏移必须发十六进制（固件用 `%lx` 解析）；
- ESP 的 `pipe=on` 可能指向一个僵死连接：数据会写到旧 socket 上（现象：`tx` 在涨但本机收不到），此时重启 ESP 即可；
- STM32 断电会连 ESP 一起重启（ESP 从板子取电），IP 会变。

## ✅ 2026-10-25 · 无线烧录全链路打通（spool / 全量缓存）

```
上传 11176 字节（44 片，每片 CRC-16 校验）   ✅
#Z 整镜像校验                                ✅
#F 自烧录: reset → sync ok → erase ok
          → write 4096 / 8192 / 11176 → ok   ✅ 2459 ms
端到端 7 s，烧完 MCU 回 +PONG                   ✅
```

**真因（两个都必须修）**
1. **上传偏移量进制不匹配**：固件用 `%lx`（十六进制）解析 `#S <偏移>`，主机却发十进制 → 偏移被放大，分片被拒。现在主机统一发十六进制。
2. **不要给 AN3155 帧加人工间隙**：中途我为了"擦除"给命令对/地址帧/数据帧加了 10 ms 逐字节延时，结果 `0x31` 直接不 ACK。**恢复成每帧一次写完**（`uartSend(pair, 2)` / `uartSend(frame, n)`）后一切正常——这块板要的正是"连续发送"。

**最终时序参数**
| 项 | 值 |
|---|---|
| 命令对 / 地址帧 / 数据帧 | 各自一次写完，无人工间隙 |
| 等待 ACK | 命令 5 s，数据 60 s，擦除 45 s |
| 分片大小 | 256 字节，两次握手（`+S begin` → 负载 → `+S ok`） |
| 整镜像校验 | `#Z <CRC16>` 通过才允许 `#F` |


## ISSUE-001 · 全量缓存（spool）固件联网即重启循环（未修完）

**现象**

  ```
  [bridge] boot board=ESP32 link=spool
  [bridge] creds src=none ssid= passLen=0
  ```
  之后没有 `join build ...`，网络里也扫不到它（3333 不通）。

**已修复的两个确定性 bug（都已进代码）**
1. spool 版从未调用 `LittleFS.begin()` → `#I` 永远返回 `+I err nofs`。已改为**懒挂载**（首次 `#I` 时挂载并在失败时格式化）。
2. 挂载代码最初被插进了 `PINSET` 分支而不是 `setup()`（已挪回）。

**尚未定位**
- 懒挂载版本仍然"启动后卡在 creds 之后"，疑似进入重启循环。
- 候选原因：① 供电余量不足（spool 版大 42 KB + LittleFS 的 flash 写入抬高电流峰值）；② 我的 spool 解析分支在某个路径上阻塞；③ 别处崩溃。

**下次要做的（按顺序）**
1. 烧入带诊断的 spool 固件，看 `[bridge] reset=<poweron|brownout|panic|task_wdt>`：
   - `brownout` → 供电问题，换 USB 口/加电容/加强共地，不是代码问题；
   - `panic` → 按 backtrace 修；
   - `poweron` → 继续查 spool 分支是否阻塞。
2. 若仍无解，先用 stream/block 交付，spool 作为后续增强。

**已经就绪但未验证的能力**（代码已写完、9 种编译组合全通过）

## ISSUE-002 · 这颗 F407 的 ROM 引导程序不接受 write memory（0x31）

**状态**：`0x31` 地址阶段确认无法通过（2026-10-25 结论）

**最终证据（冷启动 + 干净同步态）**
| 步骤 | 结果 |
|---|---|
| `0x7F` | `79` / 同步态下 `1f`（符合 AN3155） |
| `0x02 FD` gap 10 ms | `79 01 04 13 79` ✅ |
| `0x31 CE` gap 10 ms | `79` ✅ |
| 地址帧 Flash `08 00 00 00 08` | `1f` ❌ |
| 地址帧 **SRAM** `20 00 00 00 20` | 无回应 → `1f` ❌ |

**结论**：连不带写保护的 SRAM 都被拒 → 既不是选项字节写保护，也不是帧格式（与 `lee-lord/esp8266_stm32_isp` 逐字节一致、连发/加间隙都试过），
而是这颗芯片的 ROM loader 在 `0x31` 之后不接收地址帧。**这块板子无法用 UART 引导程序烧写**。

**可行替代**
1. ST-Link（已验证：约 3.8 s 一次成功）；
2. 自研 bootloader + OTA（参考 `brachiGH/STM32_OTA_updater`），需要改动 STM32 工程代码；
3. 换一颗正品 F407（同流程再验一次即可确认是"这颗芯片"的问题）。
